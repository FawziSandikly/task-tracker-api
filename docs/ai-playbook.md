# My AI Playbook

A personal guide for when and how to use AI responsibly, based on this course.

---

## When I Reach for AI First

**Infrastructure & Configuration**
- GitHub Actions workflows, CI/CD pipelines: AI excels at boilerplate structure
- Dockerfiles, container configuration: Good templates, best practices well-known
- Environment setup, dependency management: Low risk, easy to test

**Documentation**
- README updates, docstring templates: AI helps organize and polish
- Test coverage reports, evidence logging: Good at structure and formatting

**Testing**
- Pytest fixture scaffolding, test case structure: AI understands common patterns
- Debugging test failures by reading error messages: AI can suggest next steps

**Code Review & Spot-Checks**
- "Review this diff for common security issues": AI finds hardcoded credentials, non-root users
- "What does this error message mean?": AI translates stack traces

---

## When I Do NOT Reach for AI First

**Core Business Logic**
- Task status transitions, validation rules: I must understand the existing code deeply first
- Database schema changes: Requires knowing current schema and impact
- Why: AI can generate code that looks right but breaks subtle requirements

**Security Decisions**
- "Should we allow CORS from *?" → No, I decide; AI only suggests
- "What's the safest way to handle this?" → I research and verify, AI is a second opinion
- Why: Security choices are architectural; AI's job is to flag risks, not make decisions

**Learning Goals**
- If the course is teaching me about pytest fixtures, I write one myself first
- If I'm supposed to learn Docker, I read the docs before asking AI to generate a Dockerfile
- Why: The point is to learn, not to skip ahead

**Production or Real Data**
- Never paste customer data, logs, credentials, or .env files
- Never ask AI to generate data handling code before I understand GDPR/privacy rules
- Why: AI tools may log or index this; data breach risk

## My Non-Negotiables

### Rule 1: No Secrets Ever
- Never paste .env, API keys, database passwords, tokens
- Never ask AI to guess what a secret might be or "infer" credentials
- If I need help with secret management, describe the problem without examples
- **Applied in this project**: AI never saw our actual database path or config values

### Rule 2: Test Before Committing
- Every AI-generated code file must pass local tests before push
- If tests don't pass, I debug or reject the AI output; I don't commit broken code
- One line of code I don't understand doesn't get committed
- **Applied in this project**: Ran `docker build`, tested /health, ran `pytest` before committing CI workflow

### Rule 3: Diff Review is Non-Negotiable
- I read every line of AI output before accepting it
- If I can't explain a line, I rewrite it or reject it
- Copy-paste without understanding is the fastest way to introduce bugs
- **Applied in this project**: Reviewed Dockerfile line-by-line, understood every RUN and COPY command

### Rule 4: Document Your Decision
- If I reject or correct AI output, I write it down (why, what I did instead)
- If I accept it, I note the verification step
- This proves I didn't blindly accept—I made a judgment call
- **Applied in this project**: docs/final-ai-review.md logs every major AI output and my grade

### Rule 5: Understand the Context
- Before asking AI to change something, I read the existing code
- I tell AI what I learned, not just what I want: "The project uses SQLModel, not SQLAlchemy; here's why"
- This grounds AI in the actual codebase, not a generic Python project
- **Applied in this project**: AGENTS.md tells AI the full tech stack and project rules upfront

## My Review Rules

### For Code Generated by AI

1. **Ask three questions**:
   - Does it match our tech stack and existing patterns? (Would it pass code review from a teammate?)
   - Can I run it right now and verify it works? (Is it tested?)
   - Can I explain every line to someone else? (Do I understand it, or did I just copy-paste?)

2. **Grade it**:
   - **Useful**: Saves time, correct, I understand it → Accept
   - **Noise**: Correct but verbose, adds complexity → Simplify or reject
   - **Wrong**: Incorrect, unsafe, or violates project rules → Reject outright

3. **Verify it**:
   - Run tests: `pytest`
   - Run Docker: `docker build && docker run`
   - Manual check: `curl`, inspect files, read logs

### For Security Findings from AI

1. **Check the evidence**: Does the AI point to a specific line of code?
2. **Reproduce it**: Can I confirm the risk with my own testing?
3. **Evaluate impact**: Is this a real risk or a false positive (too strict, not our threat model)?
4. **Decide**: Fix it, document it as accepted risk, or reject as noise

### For Suggestions I Reject

1. **Document why**: "This uses `continue-on-error: true`, which hides test failures"
2. **Show what I did instead**: "I rewrote it to fail fast"
3. **Explain the principle**: "CI should fail loudly so we catch bugs early"

## What I Am Still Figuring Out

- **When to ask for help vs. debug alone**: I defaulted to research and manual testing, but on a team, knowing when to ask might save time. I'm learning to balance self-sufficiency with collaboration.

- **How much context to give AI**: I gave AGENTS.md and project history, which helped. But for future work, I wonder if I can be more surgical—asking about specific 20-line diffs instead of whole files. This might reduce hallucinations.

- **How to push back on AI without seeming uncertain**: When I rejected the `continue-on-error` suggestion, I was confident in the course rules. But for edge cases where I'm unsure, I sometimes second-guess myself. I'm learning to log my uncertainty (e.g., "I'm not sure if this is a false positive") and move on.

- **Tools beyond ChatGPT**: This course used AI chat. I'm curious about semantic code search, AI-assisted debugging tools, and whether pair programming tools (like GitHub Copilot in an IDE) change my review rules. They might insert code continuously, making diff review harder.

## Decision Card (Quick Reference)

| Situation | Reach for AI? | How |
|---|---|---|
| **New feature request** | ❌ No | Ask stakeholder first; I decide scope |
| **Write a test case** | ✅ Yes | Ask for structure, then code manually if complex |
| **Debug a CI failure** | ✅ Yes | Share error logs (no secrets), ask "what does this mean?" |
| **Infrastructure (Dockerfile)** | ✅ Yes | Ask for scaffold, review every line, test locally |
| **Security decision** | ⚠️ Ask for help, I decide | AI suggests risks; I evaluate and choose |
| **Paste a .env file** | 🚫 Never | Describe problem without examples instead |
| **Accept code without testing** | 🚫 Never | Always run tests, inspect diffs, verify locally |
| **Something I don't understand** | ⚠️ Ask AI to explain | If it can't explain it clearly, it's too complex; reject |
